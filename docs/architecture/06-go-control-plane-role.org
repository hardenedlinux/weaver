* Architecture decision

The production target is Rust + Scheme/POO/gerbil-ascent. Rust owns network I/O,
bounded queues, durable state and final effects. Scheme owns higher-order
configuration, object composition, rule inference and Workflow semantics. Go
is optional for concrete integration/development reuse; it is not a required
planning hop in the target architecture. R2's default source-preparation command
exits before fixed or catalog-selected operations reach Rust directly. Only
explicit =serve= retains the Go relay for reference controls and R5 retirement.

The model authority is [[file:../../dev/sysml/ArchitectureEvolution.sysml][ArchitectureEvolution::RustSchemeAllocation]],
linked to [[file:../../dev/sysml/WeaverExecution.sysml][WeaverExecution]] and the existing source, ledger and object-lifecycle
contracts. The [[file:../50-59-research-program/59-provider-rpc/59.87-spec-upgrade-and-delivery-plan.org][delivery plan]] records the implementation matrix, finite acceptance,
failed evidence and retirement order. R1 does not qualify the outstanding 1 ms
latency gate or establish exact-head GitHub CI.

* Current ownership after R1

| Responsibility | Owner and existing mechanism |
|----------------+------------------------------|
| Decode external JSON/YAML syntax and copy typed data | Existing Go file adapter; no semantic selection |
| Candidate eligibility, exact rounded cost/latency/digest ranking | Scheme POO records and gerbil-ascent on the existing affine owner |
| Session topology, nested choice/parallel/join and ready-node derivation | Existing Scheme Session/Funflow/Governor and ASCENT |
| Canonical plan/body commitments and request/profile/endpoint guards | Rust contracts and shared HTTPS transport guard |
| Configuration/source proposal delivery | Existing authenticated source gRPC; Go currently transports the data |
| Catalog observation and typed fact projection | Existing Rust source owner and ledger; no second database |
| Immutable projection reuse | Existing version/record cache and bounded coalescing; no cached permission |
| Publication, exact source/currentness, claim, reservation, hard-fact barriers | Existing Rust deciding transactions |
| Credentialed request, streamed response release, fallback and uncertain outcomes | Existing Rust broker/runtime; R2 fixed/catalog callers connect directly, retained relay callers use serve |
| Independently issued SPEC review and terminal usage signatures | Existing separate issuer custody; language migration cannot merge keys |
| OpenSysML analysis, model rendering and development drivers | Go, retained for direct existing SDK reuse |

The Go routing/Bundle algorithms still have development/reference callers.
Deployment bootstrap and dynamic request materialization no longer invoke them.
Their later physical removal follows consumer migration; there is no second
production selector or Workflow runtime in Go.

* Composition and authority are different boundaries

Startup catalogs can declare an already composed original or a bounded source
composition, never both. The existing Scheme owner composes the latter, Rust
validates it, and only then seals the exact original. Later CompileSource calls
still compare the candidate against independently retained original data with
SourceExpectation equality. No request can replace an installed producer.

File-source and dynamic catalog inputs use source-only ComposeSource. The RPC
returns inert data; it cannot publish, install a catalog, enroll a source,
resolve a hard-fact barrier or produce a consumed permit. Source authority is
checked before and after derivation. Catalog-backed requests require the exact
observed version and recheck it afterward. Full source assessment remains in
CompileSource; pure composition does not delay listener readiness with module
source evaluation. Rust keeps fresh deciding checks at actual use.

The Go adapter copies independent SPEC review data without regenerating it.
A new candidate or source response cannot self-approve the publication it
suggests. See [[file:09-code-as-policy.org][Code as Policy]], [[file:05-authorization-execution-protocol.org][authorization-to-execution coordination]] and
[[file:13-go-adapter-broker-boundary.org][adapter-to-broker custody]].

* Request and cloud-adapter separation

Target request path:
client -> Rust ingress/admission -> prepared projection or necessary bounded
Scheme derivation -> Rust ledger/Cedar/claim/reservation -> broker -> response
release. Complete released receipts drive the existing Governor progression;
a pending queue entry or a historical receipt is not permission to send.

Target configuration/fact path:
file or authenticated cloud observation -> Rust source adapter -> existing
persisted intent -> Scheme/POO/ASCENT impact/reconciliation -> existing Rust
prepare/publish/activate transactions -> observed status. Scheme derivation
cannot release a barrier; the deciding transaction checks exact source revision
and intent prefix. There is no Kubernetes API access in response forwarding.

Cloud observations retain cluster/resource identity, UID, opaque resourceVersion
and generation separately from ledger revisions. Duplicate/reordered watch
notifications, relist, deletion/recreation and reconnect cannot revive revoked
facts. Coalesce recomputation demand, never accepted intent or unknown holds.
Kubernetes leader election, Programmed status and xDS ACK are observations;
they do not fence old workers, resolve uncertain effects or free shared quota.

Use separate bounded adapter queues, concurrency and credentials even when an
adapter and runtime share Rust/Tokio. A slow controller, collector or control-plane
outage cannot consume the frame writer's execution budget. See the existing
[[file:14-stream-message-authorization.org][stream-message contract]] for immutable messages, credits and complete release.

* Long-term cloud-native reuse

Language choice follows the required integration and its existing evidence:

| Existing evidence | Allocation decision |
|-------------------+---------------------|
| kube-rs client/controller/CRD interfaces and Praxis Grid's Rust dependency set | Rust is a viable default for Kubernetes; implementing it does not require a Go controller |
| Agentgateway's Go controller dependencies include Kubernetes, Gateway API, Istio, Helm and xDS | Go can aggregate substantial integration machinery when those exact capabilities are required |
| Helm pkg/action provides release lifecycle APIs | An embedded Helm lifecycle can justify a separate Go deployment adapter; ordinary chart installation need not be embedded |
| containerd exposes a rich Go client and remote service APIs | Choose protocol access or a Go SDK by required lifecycle behavior; do not turn the gateway into a container orchestrator by default |
| OpenTelemetry Collector is independently deployed and Rust has an SDK | Reuse the Collector through its interface; its Go implementation does not require embedding Go |

These decisions use upstream source/interfaces and maintenance evidence. Weaver
need not implement both ecosystems or rerun generic ecosystem benchmarks to
justify them. Local tests check our integration's authority, behavior, failure
handling and actual runtime gates. No speculative Go adapter or generic plugin
host is added solely to retain a language.

* Delivery and retirement order

1. R1: consolidate deployed source selection/composition in Scheme and Rust;
   retain OpenSysML and finite existing reference controls.
2. R2: replace the Go request/frame relay with direct authenticated Rust ingress,
   preserving OAuth first-hop binding, trailers, cancellation and complete release.
3. R3: finish startup/source lifecycle consolidation through existing owners and
   ledger transactions; preserve restart, withdrawal and A-to-B-to-A behavior.
4. R4: add the first required cloud integration, Rust by default, with an isolated
   Go adapter only where upstream SDK evidence selects it.
5. R5: remove obsolete production Go packaging and reference algorithms after all
   consumers migrate; decide development tooling and independent issuers separately.

Finite R1 evidence and remaining gates live in the delivery plan. Compile,
listener readiness, first source assessment, hot execution and drain are separate
measurements. The same release and original acceptance thresholds apply; a
language-placement change alone does not satisfy the outstanding 1 ms target.
