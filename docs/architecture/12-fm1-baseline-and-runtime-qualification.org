* Decision: greenfield consistency, not backward compatibility

Weaver is a new framework. It does not require compatibility with old Gateway
APIs, old Policy encodings, old process layouts, or existing native object
files. Do not introduce a compatibility shim, dual semantics, legacy parser,
version adapter or automatic downgrade merely to preserve reference pins.

FM1 asks a different question: can the selected components constitute one
reproducible semantic and execution baseline? Cedar meaning, compiled proofs,
serializers, supported features and native calling conventions must agree
within that baseline. New software still needs its own components to agree.
Interoperability with selected HTTP, agent and Kubernetes protocol standards
remains required; that is separate from preserving an old Weaver API.
Calling baseline consistency backward compatibility obscures the design decision.
The preferred term is =baseline consistency and native qualification=.

Research pins identify evidence; they do not dictate Weaver's future dependency
manifest. This review leaves all pins unchanged and tests the exact referenced
owners separately. A future direct migration can deliberately select one
semantic revision and rebuild/port its consumers, with fresh evidence. It need
not run old and new semantics together or import old authority.

[[file:11-source-to-execution-assurance-review.org][The preceding source review]] retains the historical observations. This document
records the isolated dependency/native investigation using C7/C12/C13,
P9/P11/P36-P41 and T1-T7 in [[file:01-reference-comparison.org][the source register]], and the resulting target
selection. No new gateway code, theorem, model, ABI shim or dependency override
is introduced.

* Native ABI boundaries to qualify

** Existing POO native path

The existing Runtime.CedarNative owner decodes Cedar protobuf, calls
Cedar.Spec.isAuthorized and exports =poo_flow_cedar_authorize_native=. Its
outcome explicitly identifies semantic revision e9fa9c1; Rust wire validation
expects that revision. Linking a different evaluator under the old identity
would be false provenance, even if several allow/deny examples agreed.

The native probe and Runtime Host C sources declare generated initializer
symbols taking one uint8_t argument for the pinned Lean 4.31 owner. They consume
an owned ByteArray and receive an Except that owns its String. The Host copies
String bytes before releasing the Lean result; Rust frees the copied allocation
through the same C allocation owner. Initialization and calls have a declared
thread/process lifetime. These are private implementation obligations, not a
stable cross-version ABI promise.

The probe checks inherited SIGCHLD state, repeated calls, output identity and
malformed-input rejection. The AOT Host additionally needs the Rust static
archive, actual linked component identities, independent worker execution,
deadlines, typed failures and the existing authority tests. Symbol presence or
a successful link is insufficient to establish those properties.

** cedar-poo-spec foundation and new Weaver target

The pinned cedar-poo-spec Rust bridge exposes Rust library/CLI policy artifact
and replay APIs. Its own build is not the POO Lean/C initialization ABI or an
already implemented Weaver final broker. Its Lean library is a semantic/proof
foundation, not an emitted execution capability.

The inspected generated C in both the old native owner and the new
CompoundAuthorization library uses a one-byte initializer argument. No
initializer-arity incompatibility was established by this comparison. Matching
that shape is also not proof of heap layout, runtime, linkage or ownership
compatibility; Weaver has no need to share old native objects.

A new Weaver native component must generate/inspect its own C exports and
initializers with the selected compiler, link objects from that same dependency
closure, and qualify ownership, thread/signal behavior, panic/malformed input
and shutdown. No requirement exists to accept the POO 4.31 .olean/.o/.a files
in a Lean 4.34.1 process. The reference service protocol can inform a new contract,
but old message IDs or accepted payloads are not automatically retained.

A process boundary avoids sharing Lean heap objects across services; it still
requires exact schema, feature, diagnostics, artifact and semantic admission.
Neither process separation nor an adapter translates away mismatched semantics.
In the reference topology Go has no required Lean heap/C ABI edge: cloud-native
coordination uses admitted messages and explicit observed state. Scheme owns
source/lifecycle semantics; its exact callback/bridge must be qualified with
the selected Gerbil/Rust artifacts. Rust owns its private native evaluator glue
and physical coordinator/broker guards. Do not create a Go-to-Lean C ABI merely
to imitate an upstream language split.

** Fresh malformed-input finding and target consequence

The isolated old native probe exits 1 with an out-of-bounds panic on the
single-byte truncated varint ff; typed rejection requires exit 2. The stack
identifies Proto.find_end_of_varint_helper. Empty protobuf produces default
deny across 128 calls with SIGCHLD preserved. These are actual executions,
not a source-only inference, and the successful input does not cancel the
failed malformed-input gate.

Protobuf/Varint.lean is byte-identical in the two Cedar pins, with SHA-256
438f742e802a98c8f0bd099bee6d61c490960de3d7d38f01dfe7c8e908f3527c.
Its check observes the original cursor while indexing pos+n. The selected
new native entry has not been implemented or exercised, so this is a shared
source risk rather than a newly reproduced 4.34.1 binary failure. Merely
selecting the newer semantic tuple cannot be presented as repairing the parser.

Do not inherit raw protobuf decoding merely to retain the old boundary.
The new entry must qualify an owner-repaired decoder or a deliberately selected,
bounded input contract with a proved projection into the actual Cedar inputs.
A Rust preliminary check is insufficient unless its acceptance contract makes
the remaining unsafe input unreachable and that relation is validated. Worker
isolation contains a panic; it does not turn panic into successful evaluation
or satisfy the strict typed native-parser gate. No owner parser is patched here.

* Recommended selection and direct migration boundary

Core design is shown in [[file:09-code-as-policy.org][Cedar inside the Zero Trust gateway]]. Version pins,
build counts, failed probes and qualification receipts remain in this document;
they are not architecture components or diagram labels. This is a design
recommendation, not a pin change or a completed Weaver build.

Recommend cedar-poo-spec c8d1a06 with its declared Cedar 017c35c, Lean 4.34.1,
LeanPoo ccb94dc and batteries f2effa3 as the semantic foundation candidate for
Weaver. Evaluate Cedar Rust 4.12.0 using the exact enabled feature intersection
and independent semantic/protobuf vectors. This favors the required owner
foundation over freezing a new framework to POO's older native evaluator.
It does not claim that Cedar Rust and the selected Lean revision have already
passed complete equivalence or native qualification.

Reuse POO's public semantic contracts, lifecycle/recovery laws and tested
ownership patterns at source level. Port the affected consumer definitions,
request projection, full diagnostic identity and generated native glue to the
single chosen baseline as later owner-scoped implementation work. Do not import
a second Cedar semantic owner into the same Lean package to avoid that work.
The unchanged POO 4.31 tuple remains reference evidence for its own old native
path; it is not a required compatibility target for Weaver.

The direct migration boundary includes policies/schema/entities, required
layers, canonical subject/handoff representation, source admission, runtime
witnesses, generated ABI, Host identity and every receipt consumer. New
identities must honestly denote new semantics; do not relabel old binaries.
Old serialized grants, local reservations, affine handles or receipt signatures
cannot be promoted to authority in the new incarnation.

For a genuinely empty deployment, initialize a new admitted lineage. If an
operational cutover carries existing obligations, stop/drain or retain the old
emission conflict domain, resolve authoritative commands, and carry restrictive
history and unsettled exposure through an explicit admitted migration record.
Greenfield API freedom does not permit discarding liabilities or forgetting a
possibly live old worker. Imported history is data/evidence, never a revived
execution capability. An unresolved cutover remains quarantined.

* FM1 disposition for the new framework

The investigation establishes two independently buildable owner tuples and
actual old-tuple native/Host evidence. It does not establish that a backward
compatibility layer is necessary. The recommended new semantic foundation has
successful full owner builds, Rust tests and a bounded cross-engine schema
slice. The new gateway consumer/native entry has not been implemented, so its
full FM1 admission cannot yet be claimed. The shared parser risk is a concrete
qualification obligation, not a reason to retain two semantic engines or hide
a failure behind an adapter.

A profile enabling the new source-admission bridge must also bind the selected
Lambda Aitia/Scheme owner, its evaluated issued-family extension, private runtime
artifacts and complete P15 callback/lease evidence. The old Cedar primitive
checks do not exercise that currently absent protected path. Neither a passed
Cedar package suite nor a passed old authority fixture closes FM3-FM12.

No source patch, dependency pin/manifest update, new implementation or production
release is authorized by these qualification results. Later implementation
should adopt the chosen baseline directly, with owner-scoped migration and the
explicit invalidation/acceptance obligations above. Preserve every failed,
environment-restricted and successful receipt at its actual scope.
