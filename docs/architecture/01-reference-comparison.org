* Zero Trust comparison and limits

ZR1 rejects implicit trust based on location or asset ownership. Weaver adopts
this as a required design baseline with scoped authentication and authorization,
not as a certification obtained by using a gateway.

ZR2 describes OS containment plus action-level enforcement through an egress
gateway, interpreters, and MCP broker. Shared event history can connect actions
across tools, and the gateway can attach credentials outside the workload.
The announcement also distinguishes directly granted filesystem access from
policy-observed activity and acknowledges a larger trusted computing base.
These observations motivate explicit coverage and trust inventories in Weaver;
they do not establish complete mediation for every deployment.

ZR4 excludes within-process multi-tenant isolation and points to external
isolation for that threat model. It treats credential misrouting, reflection,
and redirects as security-boundary concerns. Weaver must qualify its own
isolation and credential broker, rather than inherit protection from a language
choice or upstream product description.

ZR5 describes serialized, persisted event admission and compact temporal
summaries. It also states that new temporal policy clauses use post-update
history. Weaver cannot adopt a fresh-history convention where it would erase
existing data-flow restrictions: migrate/rebuild qualified state or deny the
affected capability until its required history is available. Stateful temporal
decisions need their own selected semantic/state owner. No equivalence between
Dogwood, Cedar, or POO Flow temporal semantics is claimed.

* Cross-review: agreement is not an error-free runtime permit

P26's =Outcome::agrees_with= compares decision, determining-policy IDs and
erroring-policy IDs. Its validator permits nonempty erroring IDs distinct from
determining IDs. P23 validates matching witnesses. P5's =Authority::issue=
branches on deny versus allow after evaluation, with no explicit rejection of
nonempty =erroring_policies= on that issue path. P27 separately calls
=require_error_free_decision= in case qualification. That separate case check
is not evidence that every runtime issue call enforces Weaver's error-free
execution profile. This is a source-level gap, not a reproduced exploit.

The new source-admitted authority path must reject error-bearing results before
issuing its executable grant; until that extension is qualified, it stays
unavailable. An additional consumer-side rejection is defense in depth and does
not replace the issuer requirement. Do not claim that strict lockstep already
supplies this behavior or change Cedar's own decision semantics.

The language reference describes [[https://docs.cedarpolicy.com/auth/authorization.html][default deny, forbid precedence, and skip-on-error]].
Weaver's stricter admission rule is application policy. The online reference
clarifies terminology; the listed source commits remain the implementation
baseline. See [[file:09-code-as-policy.org][Code as Policy]] for its complete artifact and enforcement chain.

** Useful agentgateway mechanisms

A1 describes separate startup settings and dynamic resources, shared IR,
and resource references that limit update fanout. Weaver should reuse the
principle while adding dependency-closure activation. A1 does not establish
cross-resource atomic activation or a Weaver security proof.

A2 analyzes expression dependencies at configuration time to retain only
needed request data. It also documents incomplete detection for dynamic
access. Weaver therefore requires conservative dependency capture: uncertain
access retains bounded data or rejects the plan; it must not silently omit a
security input.

A3 distinguishes request policy execution from per-backend-attempt execution.
This is a useful basis for retry semantics. A8 exposes typed request/response
state and host-selected backend dispatch. Weaver should adopt explicit
phase capabilities without treating arbitrary callouts as trusted facts.

** Authorization behavior that requires an explicit decision

At A4, =RuleSets.validate= permits access when there are no rules. It also
permits when only deny rules exist and none matches. Allow rules use an
allowlist default, and all require rules must match. The source comments
warn that a deny expression error can fail to deny.

Weaver protected capabilities require an installed Provider and a valid
positive authorization result. Missing policy, unknown capability, invalid
input, evaluation failure, and unavailable authority cannot become a permit.
This is an application admission rule around Cedar; it does not change the
upstream semantics of policy evaluation errors. A valid Cedar deny remains
distinct from an invalid or failed evaluation.

CEL remains a possible operational-expression adapter. No CEL-to-Cedar
semantic equivalence has been established here. CEL filters cannot create
grants or bypass required Cedar evaluation. Automatic translation would
need a defined supported subset and a semantic preservation argument.

** Avoid inference from dependency presence

A7 currently constructs runtime stores around =Arc<RwLock<...>>=. A9 listing
=arc-swap= does not prove that all configuration reads use immutable atomic
snapshots. The relevant store and request path must be inspected and measured
before making lock-free or update-consistency claims. Weaver's immutable-plan
design is a proposal with its own reclamation and contention obligations.

* POO Flow integration findings

P1 owns engine-neutral Governance in POO Flow; domain contributors select
profiles, cases, sources, and policies. P2 constructs inert Provider and
Capability values with =runtime-executed? #f=. Weaver preserves that boundary.

P8 does more than load an exported policy file: it compares schema, entities,
policy identities, and rendered sources against a POO-owned snapshot. The
validated Lean artifact constrains that snapshot; it cannot publish an
authority on its own. A Weaver publication path must preserve this join.

P5 binds grants to authority instance, runtime generation, policy revision,
revocation epoch, authorization subject, intent, and exact handoff. Issuance
is pending issuer state. Consumption removes that state before returning the
handoff; an external execution failure does not reopen the grant. This is
single-use issuance behavior, not exactly-once execution across a network.

P7 runs Rust and Lean workers sequentially under one shared deadline. It
starts private executable copies per request. Worker startup, input staging,
evaluation, and receipt work belong in the critical-path budget.

P6 rejects capabilities requiring source admission through the ordinary
preparation path. P4 says a trusted current-Decision path is not installed
there. Weaver must not infer production effect authority from an unmarked
request or a permissive Cedar policy. The actual application-owned path and
its currentness checks require separate integration evidence.

** Additional pure-state and authentication boundaries

P12's =poo-flow-authorized-effect-token-validate= checks binding, root, expiry,
epoch, spent-nonce input, and diagnostic durability. The inspected function
does not cryptographically verify the stored signature or authenticate its
caller-supplied validation context. P13 returns a pure next-state value; it
does not perform a durable write or serialize competing host commits. Two callers
can compute transitions from the same old state unless the Host fences them.
Names such as =strict= and =durability= describe values or intent, not storage
or authentication evidence. This is an API evidence limit, not a new exploit
claim or a substitute for inspecting the complete selected application path.

P5 independently verifies signed Rust grants and keeps issuer-owned pending
state. No interchangeability with the Scheme draft token follows. P12 hashes
Scheme-written values; P14 signs/digests through restricted deterministic CBOR.
Treat those formats as separate protocols until an owner-qualified projection
proves their relationship. Do not invent a shared digest by matching field names.

The review dispositions R1-R14 and required baseline are in
[[file:04-zero-trust-and-review.org][Zero Trust baseline and architecture review]].

** Concrete lifecycle and recovery reuse

P15 enforces an exact Scheme owner thread and rejects mutation during its runtime
handoff. It checks current request, epoch and lease, marks a grant reserved once,
and consumes a reservation before delivery or rejection. The delivery receipt
explicitly reports =durable? #f= and =distributed-authority? #f=. These are useful
existing lifecycle semantics, not a durable ledger to invent again in Weaver.

P16 fingerprints the actual issued request and preserves preflight-only markers.
Its currentness predicate is a source-owned guard, not a permit. P17 assigns
append/fsync/lease/checkpoint/repair work to the runtime backend, with Scheme
owning selection and contract projection. Backend capability negotiation must
still qualify serializable multi-row history/budget/claim operations.

P18/P19 already define durable canonical intent, exclusive recovery claim,
epoch/fence and provider/worker binding, fresh recovery authorization, and
terminal effect observations. Several validity/binding relations are parameters:
a gateway runtime must supply and justify them. P20/P21 require effect-universe
coverage and exact multiplicity for a committed exactly-once claim. A successful
HTTP write is not that witness. No fresh Lean compilation or physical recovery

** Source-admission, ledger and stale-worker refinement

P16's =decision-preflight-bound?= deliberately requires unknown state/outcome.

Source materialization copies and rehashes configured-reader inputs, while its

recreated-context rejection tests; that is distinct from a paused old process or
memory snapshot resuming with its original instance still alive.

operations, not the proposed gateway multi-row transaction and idempotent command

* Cedar POO Spec integration findings

C2 compiles explicit =extend=, =overlay=, and =remove= edits through C4-based
composition, rejects conflicting sibling edits, and retains provenance.
Weaver policy attachment must not reinterpret these edits as generic
last-write-wins updates. Changing schema invalidates schema-dependent proof
premises even when a policy body stays unchanged.

C3 distinguishes compiled static policy exports from editable templates and
links. Plain Cedar source reparsing can change policy IDs; use ID-preserving
JSON artifacts or an explicitly verified identity mapping for receipts.
Unsupported abstract syntax must fail export rather than acquire an invented
concrete meaning.

C4/C5 distinguish schema-bound validation and replay from diagnostic replay.
Schema-defined action hierarchy can affect the result. A finite replay receipt
does not authenticate the supplied facts or prove all future requests correct.
C8 binds an operation to supplied effect/state values and explicitly leaves
their authenticity and eventual execution binding to the Host.

* Reuse strategy

Three reuse choices remain available: configure an upstream deployment,
integrate upstream libraries/services, or implement a narrow independent
gateway. A long-lived fork adds security-update and protocol-maintenance cost.

Evaluate each choice against: preserving POO ownership; exact subject and
handoff binding; default-deny protected capabilities; closure activation;
Go networking integration value; strict Host cost; and artifact/protocol
compatibility. Source inspection has not established a stable embedding API
or complete fit for any choice. Record the selected commit and maintenance
owner before implementing a reuse path.
