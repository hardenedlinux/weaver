#+LANGUAGE: en
#+OPTIONS: toc:2 num:nil

* Source and artifact ownership
The isolation directory captures Core source/data roles and gerbil.pkg metadata,
excluding prior build products. POO sources come from exactly the dependency
commit already named in Core's gerbil.pkg. No package install, pin edit, upstream
source edit or global compiler/runtime replacement is performed.

The fixture body is byte-identical to the earlier eleven-check workload. The
owned entry adds only a dynamic cleanup canary and a normal-return marker. It
imports the compiled fixture and calls the public load procedure;
it does not terminate the process explicitly. Source snapshots and tool/input
identities distinguish reused installed Gerbil/Gambit/stdlib from freshly built
Core/POO/verification modules. This is not a rebuild of the entire toolchain.

* Prelude-aware source closure
A correct closure includes explicit imports, syntax dependencies and package
preludes. The initial import-only graph built value modules yet omitted Core's
module-prelude interface; execution and linking correctly rejected that incomplete
artifact set. The repaired source visitor walks prelude contexts as well.

The first isolated stage's unchanged artifacts may be reused only after their
source and artifact hashes are retained; the added prelude stage builds the
missing modules. An artifact existing on disk is not sufficient reuse evidence.
Only isolated library output is provided when building the final entry; the
shared Core/user library directories are not fallback owners for source modules.
Installed standard library/runtime artifacts remain explicit trusted dependencies.

AOT means compiled Scheme code in one program image, with ordinary dynamically
linked platform libraries. It does not mean a fully static macOS executable.
The platform SDK/runtime link settings belong to the isolated build recipe,
not architecture diagrams or a dependency migration layer.

* Native resource lifecycle
1. Start the process and the original fifteen-second monotonic acceptance clock.
2. Execute every original Contract assertion and duplicate-key rejection check.
3. Load an owned Gambit dynamic module. Its C constructor records =L= in a fresh
   per-run file. This acquisition occurs after the old completion marker.
4. Return normally from main, without calling exit/_exit or disabling cleanup.
5. Normal dynamic cleanup runs the module's C destructor, recording =U= in the
   same file. The complete sequence must be exactly =LU=.
6. Accept only natural process exit zero, within the original clock, with exact
   assertion names, original fixture/source identity, and the cleanup evidence.

A completion marker, main-return marker, stale canary file, compiler success,
late zero exit or a binary using different source must not independently pass.
Each run uses a fresh marker and process environment; filesystem caches are not
claimed cold. Hash binary and canary
inputs and retain stdout, exit and elapsed time. A dynamic constructor/destructor
canary demonstrates this actual resource path; it is not proof that all possible
foreign plugins or arbitrary programs clean up correctly.

* Qualification and Gateway authority
[[file:../../../dev/proofs/lean/NativeExitQualification.lean][NativeExitQualification]] models assertions, decoder rejection, handle acquisition
and release, main return, time progression and natural exit as distinct events.
Its initialized audit preserves source identity and requires complete checks and
empty owned handles at exit. Qualified evidence also requires the original budget.
The model abstracts the truthful observation of native events; it does not verify
GCC, Darwin, all C destructors or the native observer implementation mathematically.

A native verifier pass remains assurance evidence. The actual Gateway dispatch
still needs its real current wire/Policy guards. The Lean composition theorem
uses an actual prior LlmRouting Step to retain those guards; native pass cannot
substitute for original claim, budget, history or final broker authority.

* Build recipe and platform boundary
The source visitor is [[file:../../../dev/proofs/evidence/native-gerbil-exit/compile-source.ss][the staged prelude-aware builder]]. Its reuse table names
only artifacts produced earlier in this same isolated source build, recorded in
[[file:../../../dev/proofs/evidence/native-gerbil-exit/prelude-stage-reuse.json][the reuse manifest]]. For a new empty output directory, use
[[file:../../../dev/proofs/evidence/native-gerbil-exit/compile-fresh.ss][the empty-set variant]], with the captured build environment and source root.
Do not point it at shared Core build products.

The gxc executable stage generates the final entry and static Scheme objects.
Its retained failed system-link invocation does not become a pass. The successful
[[file:../../../dev/proofs/evidence/native-gerbil-exit/link-public-load.json][explicit final link]] uses those freshly generated object paths and an explicit
platform SDK plus system library at the end of the argument vector. This local
build recipe is recorded separately from dependency pins. The
[[file:../../../dev/proofs/evidence/native-gerbil-exit/relink-entry.py][link replay helper]] preserves that exact argument vector; use a new receipt
directory when reproducing. Installed compiler/stdlib binaries remain trusted.

The cleanup canary has two translation units: a minimal Scheme load marker and
a separate C constructor/destructor. Its Scheme C uses the installed gambuild-C
ABI definitions and the exact module linker name. Public load resolves the
resulting bundle; incompatible compiler options or private loader arity are
rejected, never normalized into a successful cleanup test.

* Reproduction policy
Use the captured source/build recipes and exact tool identity in a new isolation
and evidence directory. Do not overwrite historical sealed receipts or accept a
new source revision under an old artifact identity. Build time is recorded
separately from the unchanged process acceptance deadline. Native qualification
runs must start after builders finish; diagnostic timing under compilation is
not a performance or availability result.
