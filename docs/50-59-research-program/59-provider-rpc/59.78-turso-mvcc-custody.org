* Execution boundary

[[file:59.79-turso-final-domains.org][Independent final-effect domains]] supersedes this initial profile's global
final-send serialization. The exclusive-final-use design and receipts below
retain their historical provenance; current family final use holds shared
authority custody and the original budget/history-family mutex.

This extends [[file:59.77-mrr-turso-storage.org][the single MRR Data / Turso storage boundary]]. The service accepts
=WEAVER_STORAGE_JOURNAL=mvcc= explicitly; WAL remains the default. Both profiles
use the same pinned engine, schema, budget rules and execution code. Nonempty
databases are never converted implicitly. MVCC requires canonical =.db= paths;
Unix hard-link aliases and live journal changes are rejected.

[[file:59.77-mrr-turso-storage.svg]]

MVCC concurrency is concurrent transactions on distinct connections in one
process. The locked engine explicitly rejects multiprocess MVCC because commit
serialization, logical-log offsets and checkpoint exclusion are process-local.
The [[https://github.com/tursodatabase/turso/releases/tag/v0.8.3][official latest release]] is v0.8.3; being latest does not remove this limit.
See the [[https://github.com/tursodatabase/turso/blob/v0.8.3/docs/manual.md][native transaction contract]] and the locked database-open guard.

* Responsibilities

| Owner | Responsibility |
|-------+----------------|
| Scheme / Governor | Original semantics, profile and Policy source commitments |
| Go | Authenticated gRPC publication and routing proposals; no native send permits |
| MRR Data | Public Turso driver and native engine lifecycle |
| Rust storage | One shared Database, independent connections and process custody |
| Rust ledger | Canonical family ordering, atomic original claims/holds/consumption |
| Rust broker | Exclusive current final-use checks and private bounded transport |
| Quint | Failure schedules and unsafe counterexamples |
| Lean | Framed domain preservation and fence stability under explicit native premises |

A canonical-path weak registry retains one native Database while sessions live;
it does not cache authorization or operation outcomes. The service retains its
initial owner through complete drain. An advisory custody file is shared by WAL
processes and exclusive to the MVCC process. Its handle outlives the engine;
never unlink or replace it while an owner lives. Managed directory/file identity,
absence of out-of-band writers, and participation of all instances are deployment
premises. This is logical custody, not physical isolation or anti-rollback trust.
A second MVCC process fails closed rather than creating another coordinator.

* Transaction classes

| Class | Custody before snapshot | Native transaction | Work |
|-------+-------------------------+--------------------+------|
| Family admission/consumption | Shared database gate and canonical-family mutex | BEGIN CONCURRENT in MVCC | Request/provider enqueue/consume and range consumption |
| Global mutation/final use | Exclusive gate; drain family transactions | Immediate transaction | Policy/history/owner/schema changes, remaining mutations and final callbacks |

Family custody survives commit/abort. Hash-stripe collisions only reduce
parallelism; they do not redefine identity. Same-family nodes and effect kinds
share one original budget order. Current distinct families have independent
budgets. A future cross-family budget/history domain must acquire one canonical
conflict key before entering the parallel lane. Reconnects cannot invent a family
to evade the existing original identity binding.

All unclassified mutations remain exclusive. Parallel admission changes no
Policy, source owner, profiles, schema or other families. This excludes snapshot
write skew that native write/write conflict detection alone would miss. Schema
initialization uses exclusive custody and native immediate mode, not concurrent
DDL. Final sends remain serialized; independent admission concurrency is the
implemented improvement, not parallel final-writer throughput.

* Final-send ordering

1. Admission commits the original hold with no external send.
2. Consumption commits the original opportunity as unknown before returning a
   permit. Provider dispatch retains its separate durable one-use burn;
   request/range permits remain private and non-clonable.
3. Final use acquires exclusive custody after admissions drain, starts a fresh
   native transaction and rechecks current Policy/fence, claim, exposure and owner.
4. The bounded callback holds both custody and the deciding transaction. Policy,
   history and owner changes cannot publish between this check and actual use.
   Each later streaming release reacquires custody and rechecks authorization.
5. Errors after possible bytes remain unknown. No transaction/SDK retry,
   replacement consumption or unknown-budget refund is authorized. Fresh sessions
   recover the same original durable outcome.

If publication wins custody, old permits fail. If final use wins, publication
becomes effective after that bounded call. Submission/pending is not retroactive
revocation of sent bytes. HTTP dispatch includes waiting for response headers;
no publication latency SLO is claimed. Mutex fairness is not a proof of progress.

Native conflicts are handled before returning a new admission permit: rollback
or poison and report failure/uncertainty. There is no transparent retry. If commit
succeeded but its response was lost, canonical outcome reads recover the same
result. Restarts or restored allow Policies cannot unspend original operations.
Commit acknowledgement and filesystem durability remain native premises.

* Catalog and recovery

MVCC creates =__turso_internal_mvcc_meta=. Enrollment recognizes only that exact
name in MVCC mode, its pinned two-column shape, and exactly one expected
nonnegative integer replay-boundary row. It does not exclude a name prefix.
Similar application names, unknown shapes and extra rows remain residual state.
Closed fault copies include WAL and the MVCC =.db-log= when present; SHM is
derived. Custody files are not copied/deleted. Live copy and independent
anti-rollback protection are not provided by this implementation.
