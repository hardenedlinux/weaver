#+TITLE: 59.81 Authoritative Original Task Registration and Source Handoff
#+LANGUAGE: en
#+OPTIONS: toc:2

* Identity contract

[[file:59.80-shared-domain-authority.org][Shared domains]] now retain an additional durable original-task registry.
The source-owned task key is independent of origin, runtime family, registration
operation and source epoch. One key binds one canonical family, origin, canonical
task digest and immutable original domain-binding digest. Family and origin are
also unique in the registry. Source rotation inherits this registry rather than
allocating a new identity namespace.

[[file:59.77-mrr-turso-storage.svg]]

=RegisterOriginalTask= is a source-only typed gRPC command. It carries the exact
task, domain binding, stable task key, operation ID, expected source epoch and
optional original publication key. Existing source task APIs join the same
registry and retain their immutable source family as the initial task key; they
do not bypass it. An already explicitly registered task retains its original key
through those APIs. An execution/protocol alias cannot create a task row.

The current authenticated source is rechecked under the exclusive native deciding
transaction. Fresh commands compare the expected source epoch inside that same
transaction. The key assignment, task, origin, budget/history roots, profile and
publication linkage, and durable admission receipt commit atomically through the
existing MRR Data Turso driver. Registration performs no provider IO.

* Replay, concurrent registration and restoration

The operation digest binds the complete command and original publication key.
Reusing an operation ID for a different command fails. An identical committed
command returns the original receipt after current source authentication, even
after a source handoff; this is observation, not a new admission or execution
permission. A fresh operation must match the current source epoch. An old worker
cannot silently rebase its command or rewrite its original task key.

The stable task key is also part of private final-use stamps and fresh Cedar
context. A key mismatch between consumption, registry and historical decision is
rejected; receipt metadata is not a replacement permission for current execution.

Source rotation revokes source mutation credentials, not the meaning of every
already valid execution grant. An existing original operation still requires
current Policy/fence, original scope and consumption. Revoking those effects uses
the existing Policy/fencing protocol; source epoch alone is not an execution
revocation signal.

Concurrent registrations serialize through the existing deciding writer. A task
key already assigned to an origin rejects a different origin/family/body/scope.
A new key cannot acquire an already owned family or origin. The exact same
assignment may be observed under a new operation, but never creates another task,
claim, reservation or history entry. A failed or uncertain native commit follows
the existing poisoned-session/unknown-outcome contract; it never triggers send.

Final admission and execution now verify the original task/domain commitments
while checking shared-domain exposure and history. A surviving task whose
registry row disappeared cannot be automatically registered anew. A missing or
inconsistent original registration denies final use and retains unknown budget.
Canonicalization decodes the typed task before hashing, so map key order does not
change its meaning. Domain migration keeps the immutable declared binding and
its current root lineage; it does not replace the original commitment.

The registry also seals the original publication linkage. An unbound local task
may acquire its first publication as an additional constraint in the same source
transaction; an already sealed birth cannot be removed or replaced. Missing task
or birth projections fail registration recovery as well as final use, rather than
being silently rebuilt with a zero hold or an unrelated allowing Policy.

* Explicit issuer-trust counterexample

The first native property run found the triple relabel case: a trusted issuer
changes the source task key, family and origin together. A local registry cannot
infer that two equal task bodies represent the same real task. Identical genuine
independent tasks must remain possible. The minimized seed is retained in
=crates/ledger/tests/unit/task_origins.proptest-regressions= and has an explicit
native negative-control test and Quint issuer-trust counterexample.

The no-rebinding property therefore holds for the authoritative original key,
or a retained family/origin, not for arbitrary relabeling by a compromised issuer.
The source compiler/admission authority must carry the original upstream task
key across aliases and source handoff. Runtime adapters cannot publish source
identity or assign those keys through operation credentials. Source-owned family
keys in existing configuration paths are original declarations, not SDK session
names. This work mechanizes persistent binding and recovery; it does not prove
the truth of an external issuer's identity claims or implement content deduplication.
Coherent rollback of all durable copies still requires the independent recovery
floor; local registry equality cannot replace that deployment premise.

* Validation and performance protocol

Native proptest generates task/family/origin replacement attempts while retaining
an authoritative original identity; the all-label issuer case is tested separately
as a trust limitation. Existing Go quick.Check generated-cap/order tests now use
the actual original-task registration RPC. The new real mTLS/HTTPS test loses the
registration reply after commit, executes once, rotates source, rejects the old
live caller, restarts, observes the original receipt and rejects stale-epoch and
replacement-origin commands. The original hold/history and sole provider call
remain unchanged.

Crate-owned =ledger/task_origin_registration= benchmarks measure fresh source
admission, exact receipt replay and rebind rejection with the same pinned engine
and natural drain. Authentication and deciding SQL are measured; provisioning is
outside timing. This is the native source identity join, not TLS handshake timing.
The existing five final-use cases remain mandatory. Go validates
all eight fresh cases and the unchanged thirty-sample confidence-bound gates.
The ordinary =-clean-source check-storage= entry includes the new Quint tests and
1,000 sixty-step schedules, existing recovery models, Lean, full native/PBT and
real provider tests. No dependency pin, timeout or deny gate is relaxed.

Raw build/runtime failures and structured evidence remain ignored under =.cache=;
the minimized property seed is a reproducible test asset, not an execution log.
Initial compilation and needless-borrow failures are retained. Acceptance results
are recorded separately after verification of committed source.

The first complete cohort at =25ed70e= failed the unchanged ledger ASP gate:
the public registration function combined too many algorithm steps. Its passing
provider/model/benchmark stages do not qualify that failed cohort, and the full
native integration target did not run after the library gate failed. Recovery,
command validation and fresh installation were split into named private steps;
the focused ledger gate then passed all 30 library checks. The public API, native
transaction ordering and failure rules are preserved. Lean additionally separates
immutable task assignment from the monotone first-publication seal: adding that
constraint cannot broaden authorization, and a sealed birth cannot be replaced.
