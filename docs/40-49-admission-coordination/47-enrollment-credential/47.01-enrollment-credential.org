#+language: en
#+startup: overview

* Finding and trust boundary
A shared Kubernetes service account proves workload eligibility, not which agent
subject owns a canonical launch. Possession of a newly supplied public key does
not prove entitlement to register that key. A bearer token naming a subject can
be forwarded. Combining those three facts still does not authenticate the first
enrollment principal. A first-writer-wins key table would merely make the attack
permanent.

The trust root is an existing independently authenticated organizational or agent
subject and a trusted producer assignment of that subject and enrollment public
key to the original canonical task. The subject authentication key predates this
enrollment request. It cannot be allocated using the same shared Kubernetes
credential or the new key's self-assertion. Subject provisioning, authenticated
assignment and uncompromised private-key possession remain explicit premises.
This protocol does not create identity from unauthenticated input.

A subject is a logical principal, not a unique machine or physical process.
Copying its private key gives another process the same principal authority.
The design detects stale authority and preserves canonical results; it cannot
identify which physical process holds an intentionally shared or stolen key.
Loss of an uncompromised-key premise is a compromise requiring revocation and
explicit recovery authorization, not a successful impersonation-prevention proof.

* Canonical plan and signed transcript
The producer publishes one immutable Plan under the existing canonical launch.
The plan contains the independent subject ID and authentication-key ID, the exact
enrollment key, issuance session, challenge, audience and enrollment-only purpose.
Its Root contains the original erased-beneficiary-key template, claim, previous
grant, profile/scope, history lineage, reservation identity and source parent,
plus the enrollment epoch and challenge. A caller cannot choose a new launch,
alias, family, budget domain or history domain to get a fresh slot.

The credential contains the entire Plan, issuer epoch, issuer-allocated stable
credential ID and authenticated issuance peer transcript. Subject authentication
and enrollment-key possession cover the same canonical bytes: protocol/domain
separator, tenant/issuer audience, purpose, canonical launch, original commitment,
subject, both key IDs, credential ID, epoch, challenges and session binding.
A sender-constrained subject credential is required; a bearer-only Kubernetes or
OIDC token is insufficient. Authenticate the real peer and channel at the trusted
termination point. Caller headers, claimed SPIFFE strings and forwarded certificate
metadata are not authentic facts.

A two-stage challenge/commit exchange can offer the proposed ID and immutable
body before either proof is signed. The final CAS checks that ID is still next,
that the canonical slot and ID index are empty, and that the observed revision,
source parent, epochs, policy and full Plan still match. A failed offer reserves
no identity. Retries query the canonical launch; they do not allocate a new ID.
The Lean native verifier premise includes authentic transcript verification;
the Quint fixture represents it with explicit trusted peer facts and proof results.
Neither implements cryptography or a wire codec.

* Ordered state protocol
| State/event | Required authoritative facts | Durable result and effect boundary |
|-------------+------------------------------+------------------------------------|
| Plan | Independent producer assignment; canonical launch; original template; current root epoch | Immutable subject/key/launch plan; no new beneficiary key or execution authority |
| Issue commit | Exact Plan; subject authentication and enrollment possession; same transcript; current source/policy/revision; unused launch and ID | Credential row, ID-to-launch index and next-ID advance in one conditional durable event |
| Sign request | Exact committed credential; qualified recovery image; current source, epoch, read and policy | Persist the exact immutable signing intent before invoking the signing service |
| Sign/retry RPC | Request identifies the same committed body and credential ID | May sign the same body more than once; no new logical credential, registration or LLM effect |
| Release commit | Exact request and authentic signature for the entire body; current source/epoch/revision/policy | Retain exact released credential; return signature only after durable resolution |
| Root activation | Exact committed and released row; fresh holder proof; current bootstrap channel, source/policy/epoch/revision | Actual predecessor root registration and matching activation outcome in one authority event |
| First beneficiary binding | Actual predecessor two-key proof, original template and current parent | Preserve the original first key/session; this credential cannot overwrite the slot |
| Recovery | Independently authenticated subject or separately provisioned coordinator; current read policy; accepted recovery prefix | Return the original committed identity/body/outcome; no new ID, key, epoch, session, expiration or CAS freshness |
| Revoke | Authorized current owner; original identity retained | Advance credential epoch and actual predecessor enrollment/issuer fences; retain all historical rows and holds |

Credential publication and signing never call the LLM provider, execute tools,
activate custody, enqueue a send or release a reservation. Root activation changes
only the predecessor root registry and its outer revision; the entire invitation
and incarnation state stays unchanged. Later publication, consumption, custody
activation and final dispatch retain their existing independent gates.

* Signature release and credential forwarding
A signature is evidence of an exact issued body; it is not an offline enrollment
capability. The authoritative use path must join the committed row, signing
request, released row and current epoch, then verify a fresh proof of the enrolled
private key over the credential, original root, bootstrap challenge/channel and
current authorization context. Subject identity comes from the committed plan,
not a request override. The issuance channel and bootstrap channel are different
purposes; reusing issuance PoP as a bootstrap proof is forbidden.

A delayed signer may complete after revocation or a reply may escape before a
caller observes a later fence. The protocol does not promise to recall signature
bytes. Online current-state validation rejects the old epoch at release or use.
An SDK must not accept a valid signature alone, retry with a newly nominated key,
select another audience/purpose, or turn a callback into authority to activate.
No remote signing availability or exactly-one signing-RPC guarantee is claimed.

* Atomicity, loss of response and restart
The owner serializes Plan, credential, ID reservation, signing intent, release and
root-activation outcome through one logical authoritative commit history. Tables
may be projections in separate stores, but their successful writes are not separate
authority decisions. A callback or local projection cannot infer a committed absence.
Resolve an unknown outcome by the original canonical launch and exact command/body
against the accepted log. A pending result remains pending; never retry as a fresh
subject, key, credential ID or canonical family.

The durability premise covers the complete conditional pre/post state and independent
accepted outer prefix, including next-ID and every determining row. Checking only
the unchanged account/source floor is insufficient: credential commits can leave
both floors unchanged. Restored absence from a stale snapshot is not a free key slot.
Reconcile the accepted floor and complete projections before issuing absence/read
certificates or admitting a mutation. Fail closed if the accepted prefix or required
rows cannot be recovered. Do not invent rollback-safe durability from fsync alone.

Qualified checks credential-to-plan and ID associations, request-to-credential,
release-to-request, and both directions of root/outcome association. Missing rows,
wrong peer facts or one-sided activation quarantine downstream operations even if
a raw predecessor read has been refreshed. Historical qualification does not require
a credential to remain currently usable; otherwise revocation would make legitimate
historical reconciliation impossible. Current gates add live epoch/source/policy
checks. Coherent rollback can satisfy all pure joins, so anti-rollback prefix recovery
is a separate native requirement, not a consequence of map equality.

An old worker may retain a signature or stale observation. The final owner performs
all live comparisons and durable CAS under its current authority; a caller-supplied
new fence is not proof of ownership. Intervening commits invalidate the outer read.
Recovery queries are read-only and cannot refresh it. Reissuing transport credentials,
reconnecting MCP/A2A/Client ACP or switching Kubernetes replicas changes no canonical
launch, subject, first-key slot, claim, budget hold or history obligation.

* Language ownership and interfaces
| Owner | Responsibility | Boundary contract |
|-------+----------------+-------------------|
| Scheme / POO Governance | Original task semantics, canonical identity/profile/scope, Cedar policy compilation/evaluation over authentic facts, typed enrollment purpose and migration rules | Produces exact semantic commitment and current approval bound to authority revision; caller strings cannot manufacture subject or key facts |
| Go / cloud-native integration | Kubernetes eligibility, independent identity-provider exchange, protocol termination, channel binding and proof collection; provider-client retries and status queries | Sends immutable exact-body commands and authenticated peer evidence to Rust; cannot assign entitlement from shared SA, sign an LLM grant or interpret timeout as absence |
| Rust / authoritative broker and issuer owner | Canonical unique indexes, ID allocation, complete conditional append, signing request/release, accepted-prefix recovery, root/outcome join, current fences and actual predecessor activation | Verifies proof material and live policy facts at the determining CAS; retains exact outcomes; no callback or adapter can bypass this owner |
| Quint / Lean | Interleaving controls and fault counterexamples / arbitrary finite trace and composition proofs | Predicates for crypto, trusted assignment, durable storage, accepted prefix and current authentic policy facts remain visible assumptions |

The Go adapter passes a versioned typed envelope with canonical task ID, command ID,
expected outer/source revisions, complete Plan/credential bytes, subject/holder proofs,
channel/audience/purpose evidence and response-status query key. A native schema/codec
must define canonical encoding, maximum sizes, algorithm/domain separation, expiry,
trust-chain rotation and rejection diagnostics before implementation. Lean Nat counters
are unbounded; native counters and coordinate namespaces must reject exhaustion and
retain retired IDs. These are implementation acceptance obligations, not new pins.

Enrollment occurs off the streaming hot path. The Rust owner should produce a bounded
per-launch join certificate tied to the accepted prefix and final CAS, rather than scan
the whole registry on every message. Cached certificate or signature verification cannot
replace current revocation, policy/history, source or execution-owner checks. The final
broker remains the only application-send authority; routing, retries, redirect and partial
write rules from the execution design remain in force. No latency or throughput claim
follows from this proof.

* Recovery boundaries and unresolved native work
Automatic subject/key/session migration is not provided. Key loss or stale frozen
source parent fails closed; progress requires explicit authorized migration preserving
the canonical launch, original commitment, first beneficiary key, unknown holds and
history, or terminal reconciliation of the original task. New enrollment credentials
cannot stand in for that migration. The models prove safety, not recovery liveness.

Native acceptance must exercise forwarded bearer credentials with fresh attacker keys,
independent-subject PoP failures, concurrent ID/launch CAS, lost commit and signer replies,
late callbacks after epoch advance, inconsistent projections, coherent snapshots below
the accepted prefix, old-worker refresh attempts and first-key replacement. It must also
verify exact native decoding/channel evidence and final broker constraints. This category
adds design and executable formal artifacts only. See the [[file:47.03-proof-and-source-evidence.org][evidence and premise register]].
