#+TITLE: Embedded model client
#+LANGUAGE: en

=weaver-llm= gives a Coding Harness direct, asynchronous model access. Construct
one =Client= per application and reuse its HTTP pool on the caller's Tokio
runtime. Each call supplies the exact completion endpoint, model and credential.
The endpoint accepts HTTPS and loopback HTTP. Redirects and implicit retries are
disabled. The exchange has a deadline and cumulative response byte limit.

The client package has an independent Cargo dependency graph. Server admission,
Cedar authorization, shared budgets, persistence, Scheme and Kubernetes belong
to the Server composition. The Harness owns provider selection, its conversation,
local tool authorization and tool execution. Agent Gateway 1.7 is the reference
for provider coverage and wire behavior. This client starts with OpenAI Chat
Completions, OpenAI-compatible endpoints that implement that contract, OpenAI
Responses and Anthropic Messages. WebSocket and provider-specific auth flows
are separate protocol work. See the [[https://github.com/agentgateway/agentgateway/releases/tag/v1.7.0][Agent Gateway 1.7 release]].

| Client capability | OpenAI Chat / compatible | OpenAI Responses | Anthropic Messages |
|-------------------+--------------------------+------------------+--------------------|
| Text and function tools, buffered and SSE | Yes | Yes | Yes |
| Explicit tool choice | Yes | Yes | Yes |
| JSON Schema output | Yes | Yes | Yes |
| Plain JSON object mode | Yes | Yes | Schema required |
| User image URL or inline bytes | Yes | Yes | Yes |
| Stateless encrypted reasoning replay | | Yes | |
| Batch embeddings | Separate compatible embeddings URL | | |

The table describes the client wire adapters. Provider and model selection
determines which options are available in a deployment. For screenshots,
attach =ImageInput= values to a user =Message=. The client sends HTTPS URLs
to the provider or encodes inline PNG, JPEG, WebP and GIF bytes. Text is sent
first, followed by the images in the order supplied.

For tools, put function declarations in =Options::tools= and call
=Client::stream_turn=. Use =TurnStream::into_stream= with =tokio_stream::StreamExt=
to compose the turn with other asynchronous operations. Display =TurnEvent::Text= incrementally. On
=TurnEvent::Finished=, check the finish reason and authorize the returned
=ToolCall= values before executing them. Preserve those calls in an assistant
message and append each tool result with its =tool_call_id= before starting
the next turn. A dropped stream cancels the exchange. A truncated stream or
invalid terminal frame returns an error and yields no executable calls.
The typed stream polls the HTTP body on demand. A paused consumer can still
have bytes in the HTTP and TCP receive buffers. The exchange byte limit applies
across the whole body. Buffered SSE control frames consume Tokio cooperative
budget so they yield to other ready tasks.
=Options::stream_usage= requests terminal usage from OpenAI-compatible endpoints
that implement it. Anthropic usage comes from Messages stream events.
SSE framing uses the same =tokio_sse_codec= as Agent Gateway. The client
validates the provider's terminal event before making tool calls available.

=Options::tool_choice= controls whether the provider may call a tool, must
call one, or must use a named function from the declared tools.
=Options::response_format= requests provider-enforced JSON output. A JSON
Schema maps to all three protocol families. Plain JSON object mode maps to
OpenAI Chat Completions and Responses. Availability depends on the selected
model and the provider's supported schema subset. Assistant output remains text
for the caller to parse after the turn finishes.

Use =Client::embed= with an explicit OpenAI-compatible embeddings URL for
batches of text or token IDs. The client returns one float vector per input
in input order and checks the returned dimensions.

For Anthropic Messages, a buffered assistant message carries its ordered
=anthropic_output= content blocks, including signed or redacted thinking. For
streaming turns, attach the terminal event's =anthropic_output= to the assistant
message before continuing. Weaver checks that the visible text and tool calls
still match those blocks. Debug formatting redacts the block contents. The
caller must retain this data with the conversation; Weaver does not compress it.

The client distinguishes rate limits, context length errors and temporary
upstream failures. For HTTP rate limits it exposes integer seconds from
=Retry-After= when available. These errors inform caller decisions.
Refusals and content filters return =Error::Refused=. A refused stream
terminates without releasing tool calls or a normal completion event.

For OpenAI Responses, attach the terminal =responses_output= to the assistant
message. It preserves the ordered output items, including encrypted reasoning,
for the next request. The client requests =store: false= and submits the
conversation and corresponding tool results together. See the
[[https://developers.openai.com/api/docs/guides/function-calling][OpenAI function calling guide]].

=Client::complete= returns bounded text and completed function calls when
tools are configured. The lower-level =Client::stream= yields HTTP body
chunks that can split or combine SSE
records. For Marlin, the adapter can translate its conversation at the existing
=ModelGateway= boundary and deliver typed events to the Harness loop. The adapter
is downstream of this package.

The ignored =live_openai_responses_replays_reasoning_and_tool_output= test
qualifies two OpenAI Responses turns under one 60-second deadline. Set
=WEAVER_LIVE_OPENAI_RESPONSES=1=, =WEAVER_LIVE_OPENAI_MODEL= to an authorized
reasoning model, and provide =OPENAI_API_KEY= through the environment.

#+begin_src sh
cargo test -p weaver-llm --locked --test client live_openai_responses_replays_reasoning_and_tool_output -- --ignored --exact
#+end_src

cargo test -p weaver-llm --locked --offline
cargo test -p weaver-llm --locked --offline --test client backpressure::
cargo test -p weaver-llm --locked --offline --lib http2_paused_stream_allows_sibling_progress_and_cancels_independently

The pool test loads =weaver.toml=, prepares one profile and activates a
credential through the local OAuth issuer. Four callers share the profile on
four Tokio workers. Each opens a connection before measuring 32 turns, for
128 warm samples in total. The test checks that all turns use the four
connections and that the issuer receives one grant request and zero refreshes.
The JSON measurements report p50 and p99 for response headers, first event,
complete turn and the interval from first event to terminal. Use =--release=
for optimized measurements. Samples include the loopback HTTP exchange and
fixture work. Profile preparation, login and the first turn precede sampling.

The prepared-profile tests also cover cancellation of an incomplete SSE
response and exclusion of credential variables from a tool subprocess.

* Transport qualification

| Gate | Normal entry point | Evidence required |
|------+--------------------+-------------------|
| HTTP/1.1 SSE | Weaver client backpressure tests | Blocked peer write, ordered resume, partial-read cancellation and cumulative byte rejection |
| HTTP/2 SSE | Weaver client library target, =http2_paused_stream_allows_sibling_progress_and_cancels_independently= | TLS ALPN, one shared connection, a stalled response, sibling progress, ordered resume and a stream reset |
| Governed gRPC | Existing Weaver provider slow-consumer scenarios and Rust output backpressure tests | Bounded delivery admission, positive resume, cancellation and reconnect, rejection of revoked or replayed output |

Run correctness checks before measuring latency. For any performance
comparison, fix the revision, four Tokio workers, concurrency, payload and
frame counts, response budget, warmup and deadline. Record first event and
terminal latency separately. Keep failed runs in the comparison. A transport
result applies to the boundary and workload it exercised.

The HTTP/1.1 and HTTP/2 fixtures use four Tokio workers, 768 numbered text
frames of 16 KiB plus their sequence numbers, a 16 MiB response limit and
a five-second watchdog. The HTTP/2 fixture uses a local TLS root, a 16 KiB
stream window and a 128 KiB connection window. Its sibling and cancellation
calls verify multiplexing and stream isolation. The burst is a correctness
workload for flow control.

The observed gRPC Server fixture uses the Cargo release profile, four Tokio
workers, a three-second startup budget and a 12-second deadline per scenario.
Its provider sends 48 events of 48 KiB each. The
downstream stream and connection windows are both 64 KiB. Protobuf carries
one row per frame and Arrow IPC uses two. Prepare the Cargo test image
before invoking the Go group in a cold checkout. This separates release
compilation from the Go suite watchdog and the runtime deadlines. Run
both commands from the repository root with the same Cargo toolchain
and environment.

* Downstream configuration and credentials

The downstream =weaver.toml= describes an explicit connection
profile. A direct profile selects the provider protocol, exact endpoint,
model, deadline, byte limit and a credential reference. Keep the profile
under a dedicated local directory such as =.cache/weaver-dev/= for Snake Oil
tests. =Configuration::load= reads the explicitly selected trusted file with
Tokio. =prepare= validates one profile and resolves its credential once.
=PreparedProfile= binds the endpoint, model, response budget and pooled
client for =complete= and =stream_turn=.

| Connection | Credential provisioning | Runtime authority |
|------------+-------------------------+-------------------|
| Direct provider | The operator provisions a provider API key and supplies it through the configured secret reference | The provider authenticates the call. The Harness controls local tool execution. |
| Governed Weaver Server | Deployment supplies the operation-role mTLS identity, server trust roots and operation bearer credential | The RPC ingress checks the peer and bearer binding. Cedar and the ledger control authorized release. |
| Optional delegated provider authorization | A trusted issuer publishes a scoped grant and delivers its credential to the caller | The operation credential and delegated credential are checked independently. |

** First downstream profile

The Harness selects the profile and config path at startup. This example
uses the existing OpenAI Chat Completions codec.

#+begin_src toml
[profiles.openai]
kind = "direct"
protocol = "openai-chat-completions"
endpoint = "https://api.openai.com/v1/chat/completions"
model = "your-provider-model"
timeout_ms = 30000
max_response_bytes = 16777216

[profiles.openai.credential]
env = "OPENAI_API_KEY"
#+end_src

Supported protocol names are =openai-chat-completions=, =openai-responses=
and =anthropic-messages=. Both the profile and configuration path come from
trusted Harness startup settings. For an Anthropic direct profile, explicit
=model= and =endpoint= win; missing fields use =ANTHROPIC_MODEL= and
=ANTHROPIC_BASE_URL=. The base URL is expanded to =/v1/messages=, preserving
an existing =/v1= or =/v1/messages= suffix. An omitted credential uses
=ANTHROPIC_API_KEY=, which is included in =credential_environment()=. Other
protocols still require explicit model, endpoint and credential. Environment
values are resolved at =prepare= and the resulting profile is immutable.
An Anthropic-compatible environment-backed profile with an optional OpenAI
alternative is provided in [[file:example.toml][example.toml]]; callers select =anthropic=
when invoking =prepare=. The client never compresses conversation context.
The optional profile field =authentication = "bearer"= selects an explicit
Authorization Bearer header. Its default, =provider_default=, uses Bearer for
OpenAI and =x-api-key= for Anthropic API keys. Anthropic =sk-ant-oat= access
tokens use Bearer under the default as well. Exactly one credential header is
sent. The same selection is available through =Endpoint::with_authentication=.

#+begin_src rust
use weaver_llm::{Configuration, Options};

// trusted_config_path, selected_profile and messages come from the Harness.
let config = Configuration::load(trusted_config_path).await?;
let connection = config.prepare(selected_profile).await?;
let mut turn = connection.stream_turn(&messages, &Options::default()).await?;
while let Some(event) = turn.next_event().await? {
    // Deliver the typed event through the Harness's existing event channel.
}
#+end_src

For a mounted secret, replace =env= with =file = "/run/secrets/provider-key"=.
Relative file paths resolve against the TOML file's directory. Unix secret
files must be regular files with no group or other permission bits, such as
mode =0600= or =0400=. Provision platform ACLs on other operating systems.
Use atomic file replacement for rotation. A configuration file is limited
to 256 KiB and a credential to 16 KiB. Only trailing CR/LF in a file credential
is removed. Empty values, surrounding whitespace, invalid HTTP header bytes,
duplicate or unknown fields and ambiguous secret sources are rejected.

The provider issues the API key. The operator injects it through a named
environment reference in local development or a protected mounted file in a
managed deployment. Only the selected profile's reference is resolved.
Loading configuration does not discover files from the working directory.
The Harness must restrict the chosen path and its parent directory to trusted
inputs. Once prepared, editing TOML or the secret file cannot change a live
connection's destination, model or credential. HTTPS and the existing
loopback HTTP endpoint rules apply. The HTTP client disables redirects and
marks provider authentication headers sensitive. Errors and prepared-profile
Debug output omit credential values, endpoints and source paths.

The governed connection needs its own gRPC endpoint, server trust root,
operation certificate and private-key references, and operation bearer
reference. The deployment provisions those together. The existing Server
checks the operation peer certificate and the bearer digest at ingress.
The separate delegated provider credential is issued and revoked through
the existing grant path where enabled. Source or admin credentials do not
belong in an operation profile. Supplier login connectors define authorization
and token endpoints, client identity, audience, scopes and token lifecycle.
A desktop authorization-code flow uses the system browser and PKCE.
This TOML loader accepts =kind = "direct"= and rejects other kinds. Governed
gRPC continues to use the existing Server deployment and operation identity
mechanisms. Static direct profiles consume access tokens supplied by environment
or file. OAuth resource profiles use the shared authorization and refresh owner
below. Supplier-specific registration and identity verification are tracked as
additional connector work.

For static credentials, activate rotation by rebuilding the selected
profile from trusted inputs and swapping it for new calls. Server revocation
uses the current authorization checks for in-flight release. The direct
client depends on the provider's revocation behavior and can cancel a local
stream. Credential resolution and configuration parsing stay outside the
stream polling path. Exclude every configured credential environment variable
from tool subprocesses with the existing Tokio process builder.

#+begin_src rust
for name in config.credential_environment() {
    tool_command.env_remove(name);
}
#+end_src

The Harness must also restrict tool filesystem access to keep mounted secret
files outside the tool sandbox. Environment filtering applies to the named
references in this file. Other inherited secrets need the Harness's own
environment policy.

The =configuration::= integration group uses synthetic credentials, four
Tokio workers and a five-second watchdog per case. It verifies preparation
and explicit rotation, missing and malformed inputs, source size and Unix
permission checks, redacted diagnostics, a 307 redirect with zero accepted
connections at its destination, and tool environment filtering in a real
child process. The stream case removes both configuration and secret files
before calling the provider, then drops the prepared connection and drains
the turn to terminal success. Governed revocation and replay gates remain
the provider slow-consumer scenarios above. The downstream Harness verifies
that its selected profile reaches the Weaver client.

cargo test --release -p weaver-llm --locked --offline --test client configuration::

Weaver's implementation scope follows the reference feature being exercised.
The comparison distinguishes acquisition, refresh and attachment to an API call.

** OAuth credential owner

An OAuth profile uses =[profiles.local.credential.oauth]= instead of an
=env= or =file= reference. These settings describe a trusted resource
authorization server. The Harness supplies the browser UI and receives its
registered callback.

#+begin_src toml
[profiles.local]
kind = "direct"
protocol = "openai-chat-completions"
endpoint = "https://model.example/v1/chat/completions"
model = "chosen-model"
timeout_ms = 30000
max_response_bytes = 16777216

[profiles.local.credential.oauth]
client_id = "registered-harness-client"
token_url = "https://identity.example/oauth/token"
authorization_url = "https://identity.example/oauth/authorize"
device_authorization_url = "https://identity.example/oauth/device"
redirect_uri = "http://127.0.0.1:1455/callback"
resource = "https://model.example"
scopes = ["model.invoke"]
token_file = "auth/tokens.json"
login_timeout_ms = 300000
#+end_src

=Configuration::prepare= opens one exclusive credential owner for this file.
An existing record must match the exact OAuth settings and model destination.
Its parent directory is created with mode =0700= on Unix. Existing public
directories are rejected. Atomic records use mode =0600=.

Use =connection.oauth()= to obtain the owner. For browser authorization, call
=start_authorization=, open =authorization_url= in the system browser, and
pass the full callback URL to the consumed attempt's =finish= method. It checks
the exact callback URI, unique query parameters, state and current generation
before exchanging the code with its retained S256 verifier. For device login,
call =start_device_authorization=, display =verification_uri= and =user_code=,
then call =finish=. Device polling observes the provider interval and the
original challenge expiry within =login_timeout_ms=.

Model calls reuse a cached access-token handle. Fresh calls perform no file
or token-endpoint IO. Expiring tokens refresh through one shared Tokio mutex
before the HTTP exchange starts. Before a code or refresh-token POST, the owner
durably clears active credentials and records uncertainty. Cancellation,
ambiguous transport failure and an invalid grant require a new login. A restart
cannot reuse the consumed grant. The owner checks Bearer type, expiry and the
configured scope set before replacing tokens together in one durable record.
Store writes retain their kernel lease and serialize through completion even
when a waiting caller is cancelled. =logout= clears the record and advances
the generation, which rejects older pending login attempts.
An observed model HTTP 401 invalidates the credential used by that request
without replaying the model call. A late 401 cannot invalidate a replacement
credential. Call =shutdown= during Harness teardown to close admission and
await writes tracked by Tokio's =TaskTracker= before dropping the owner.

Dropping a turn continues to cancel its HTTP stream through the existing client.
Local logout controls new calls. Provider-side revocation and governed Server
release authorization retain their own enforcement boundaries.

The generic resource-authorization configuration rejects =openid= scopes.
The named OpenAI adapter below verifies identity before activating credentials.

** OpenAI registered sign-in

Use =[profiles.openai.credential.openai]= for OpenAI's dynamic registration
contract. The profile requires =openai-responses= and a model endpoint within
the configured resource. Issuer and resource have official defaults; changing
them is a trusted deployment decision, used by the local issuer fixtures.

#+begin_src toml
[profiles.openai]
kind = "direct"
protocol = "openai-responses"
endpoint = "https://api.openai.com/v1/responses"
model = "your-provider-model"
timeout_ms = 30000
max_response_bytes = 16777216

[profiles.openai.credential.openai]
agent_name = "your-harness"
token_file = "auth/openai-account.json"
host_id_file = "auth/openai-host.json"
redirect_uri = "http://127.0.0.1:1455/callback"
login_timeout_ms = 300000
#+end_src

Use the same =start_authorization= and =finish= interface. The initial request
uses =dynamic_agent_client=. The callback must provide a concrete issued
=client_id=, which is retained before code exchange. Returning authorization
and refresh use that issued ID. A persisted UUIDv4 host identity is shared
across account records; each account has its own protected token file and
verified subject. Email is display metadata and cannot substitute for subject.
=account_identity= exposes the verified account metadata to the Harness.

The adapter verifies issuer discovery, JWKS, an RS256 signature, key identity,
audience, authorized party, expiry, issued-at and browser nonce. Inference
permission scopes are checked separately. Returning sign-in binds the existing
subject and client ID. One login deadline includes grant exchange, metadata
retrieval, verification and activation. Fresh model calls reuse the cached
credential without fetching metadata or reading token files. JSON and SSE
Responses share this path. Treat authorization URLs and callbacks as secrets:
returning URLs can carry an identity hint and must not be logged.

=logout= durably clears local tokens before requesting remote revocation. It
retains the account registration but removes identity-token hints. Transient
revocation failures get at most three attempts; =RevocationUnconfirmed= means
local sign-out completed but supplier revocation was not confirmed. No late
revocation response modifies a newer login. These are locally qualified
protocol behaviors; they do not claim a real supplier account was exercised.

Refresh scheduling follows the documented near-expiry flow and =expires_in=.
The supplier's [[https://developers.openai.com/siwc/token-sharing-open-source/token-reference][token reference]] lists =earliest_refresh_at= without defining
its type, units or scheduling semantics. Weaver does not interpret that field
as Copilot's =refresh_in= or claim to enforce an undocumented minimum-refresh
time. This is an external contract limitation, separate from the qualified
serialization, rotating-token persistence and uncertain-grant barrier.

** Copilot device sign-in and API leases

The named Copilot adapter reuses =connection.oauth()= and
=start_device_authorization=. The Harness displays the returned user code and
verification URI, then awaits =finish=. It does not acquire credentials from a
tool subprocess or print login instructions itself. The operator supplies the
GitHub OAuth client ID of an application enabled for device authorization and
authorized for the intended Copilot integration. Weaver does not register an
application or infer entitlement from a local test. See the
[[https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps][GitHub device authorization documentation]].

#+begin_src toml
[profiles.copilot]
kind = "direct"
protocol = "openai-chat-completions"
endpoint = "https://api.githubcopilot.com/chat/completions"
model = "your-copilot-model"
timeout_ms = 30000
max_response_bytes = 16777216

[profiles.copilot.credential.copilot]
client_id = "your-device-enabled-client-id"
api_base = "https://api.githubcopilot.com"
token_file = "auth/copilot-account.json"
login_timeout_ms = 300000
#+end_src

The default device and OAuth token URLs are on =github.com=; the API-token
exchange is =https://api.github.com/copilot_internal/v2/token=. Trusted
deployments may explicitly configure =device_authorization_url=, =token_url=
and =api_token_url=, including the loopback issuer used by local tests. These
settings and the model endpoint are part of the persistent credential binding.
=api_base= is explicit: the returned =endpoints.api=, when supplied, must match
it. A different subscription or enterprise base requires a matching trusted
configuration. The prepared endpoint never follows an unapproved returned base.
The adapter identifies itself as Weaver in its editor and user-agent headers.

The owner persists the GitHub parent before requesting a Copilot API lease.
It sends the parent only to the configured API-token exchange and sends only
the resulting Bearer lease to the model. A parent with no server expiry retains
that absence; a finite parent uses its own refresh token and expiry when
provided. Parent refresh shares the existing uncertain-grant barrier and mutex.
A lost or cancelled refresh requires new login rather than replay. Missing
replacement refresh metadata preserves the previous known refresh deadline.

API leases obey both =expires_at= and =refresh_in=. The latter is the server's
renewal interval, as specified by
[[https://github.com/microsoft/vscode-copilot-chat/blob/main/src/platform/authentication/common/copilotToken.ts][Microsoft's token envelope]].
One caller exchanges a lease while others await the owner. Fresh calls do no
credential network or file IO. A failed or cancelled non-consuming GET retains
the parent for a later explicit request; it does not repeat device authorization.
An exchange 401/403 clears both stages. A model 401 clears only its matching
lease, returns the model error and never automatically replays that request.
Local logout clears both credentials and fences pending attempts. It does not
claim remote GitHub consent revocation.

** Registered OIDC acquisition

For a public-client OIDC resource service, use the named =credential.oidc=
adapter. It discovers authorization, token and JWKS endpoints from the exact
configured issuer. This reuses the existing owner, nonce/state/PKCE, private
record, refresh gate and RS256 verifier. No OpenAI dynamic registration or host
UUID is involved. The public client and callback must already be registered at
the issuer; confidential-client authentication is separate exchange work.

#+begin_src toml
[profiles.identity_resource]
kind = "direct"
protocol = "openai-responses"
endpoint = "https://model.example/v1/responses"
model = "your-model"
timeout_ms = 30000
max_response_bytes = 16777216

[profiles.identity_resource.credential.oidc]
issuer = "https://identity.example"
client_id = "registered-public-client"
redirect_uri = "http://127.0.0.1:1455/callback"
resource = "https://model.example/v1"
scopes = ["openid", "profile", "model.invoke"]
token_file = "auth/identity-account.json"
login_timeout_ms = 300000
revoke_on_logout = false
#+end_src

Call =connection.oauth().start_authorization()= and finish the retained attempt
with the complete callback URL. The ID token must bind the registered client,
issuer, nonce and selected subject. The access token needs a server-supplied
expiry and exact configured scope set. Unsupported algorithms, unsafe or
incomplete discovery and substituted records deny acquisition. Fresh resource
calls use the cached token with no metadata reads. Configuring a different
client, resource, discovered endpoint or protocol cannot rebind a saved record.

Local logout removes usable credentials and identity hints while retaining the
selected account. =revoke_on_logout = true= also requests public-client token
revocation through the discovered endpoint; an unconfirmed remote result still
leaves local credentials cleared. See the
[[https://openid.net/specs/openid-connect-core-1_0.html][OIDC authorization-code and ID-token validation contract]].

This qualifies SDK acquisition against a local signed-token issuer. The
governed profile below connects it to Weaver's operation ingress. The existing
WIF implementation remains a JWT bearer grant; it is not RFC 8693 exchange.

** Governed operation authentication

Use =kind = "delegated"= to bind OIDC acquisition, one STS, one operation
resource and the existing operation TLS/bearer identity. The model client
package prepares configuration without depending on Server or gRPC.
=weaver_server::OperationClient::from_config= consumes that prepared material
on the caller's Tokio runtime. Use its =identity()= for browser login, then
=execute= for an existing =ProviderRequest=. The typed client exposes execution
only; source publication stays on its independent authenticated lane.

Without =client_secret=, the exchange sends the configured public client ID.
With it, client authentication uses form-encoded HTTP Basic credentials.
An optional =exchange.actor= supplies =token_type=, a trusted =expires_at=
bound and a =token= environment/private-file reference. Supported actor type
URIs are =access_token=, =jwt= and =id_token= under the RFC token-type namespace.
The STS validates the actor; the SDK forwards it only to the bound STS and caps
the child to the configured actor lifetime. Every configured secret environment
reference is included in =credential_environment()= for tool exclusion.

The request uses the acquired access token as its subject, requests a Bearer
access token for one audience, resource and exact scope set, and verifies the
issued-token kind, usage type, scope and explicit lifetime. Missing response
scope retains the requested set as allowed by the protocol. Unsupported issued
token kinds, reflected credentials, refresh-token output and ambiguous results
deny activation. See [[https://www.rfc-editor.org/rfc/rfc8693.html][RFC 8693]].

The identity record also persists the child and a pre-POST uncertainty marker.
Four callers share one exchange. Cancellation or an unknown result cannot
repeat that POST after restart with the same parent. New parent authorization
clears the barrier. Known child expiry permits ordinary renewal. Child lifetime
is capped by the subject and configured actor bounds. The prepared operation
certificate/key, root, server name and bearer digest also bind the record.
Fresh acquisition reads no files or metadata. Exchange completes before the
RPC and never runs while polling its response.

The operation interceptor sends its existing Bearer identity. The exchanged
credential goes in =weaver-provider-oauth= and must differ from that bearer.
The server verifies the mTLS operation peer and still requires an independently
signed, source-published grant for the exact token digest, peer, audience and
scope. Its opaque delegated-token contract accepts 32–256 graphic ASCII bytes;
the configured STS must issue compatible tokens. No STS response publishes a
grant. A source revocation during an upstream wait blocks subsequent response
release through the existing ledger checks.

The local integration exercises the actual issuer, STS, TLS operation listener,
source publication and provider transport. It proves successful invocation
after signed approval and denies unapproved credentials, wrong peers, a correct peer with a wrong operation bearer, and release
after grant revocation. Its independent review signer is a controlled fixture,
not a claim of a SPEC semantic proof. Production still needs registered OAuth
clients, an approved STS, correctly bounded actor credentials and a trusted
grant publisher. Local acceptance does not require live provider credentials.

separate. OpenAI's current open-source sign-in contract uses dynamic registration,
per-account issued client IDs and ID-token verification. Its registered
application flow is specified in the
[[https://developers.openai.com/siwc/token-sharing-open-source/sign-in][official OpenAI registration and sign-in documentation]].
The common protocol implementation reuses
[[https://docs.rs/oauth2/5.0.0/oauth2/][oauth2-rs 5.0]] with the existing reqwest transport.

** Anthropic thinking controls and stream events

=Options::anthropic_thinking= selects adaptive, manual budget or disabled
thinking, and =anthropic_effort= selects output effort. Availability varies by
model and provider. Manual thinking requires at least 1024 tokens and a larger
=max_tokens=; DeepSeek documents that it ignores the manual budget. Other
protocols reject these Anthropic-specific options. Omitted controls defer to the
provider. =TurnEvent::Thinking= yields provider-returned thinking separately
from final-answer text. Its debug representation omits the content; callers
choose whether to display or store it. Terminal =anthropic_output= remains
necessary for lossless continuation, including signatures and redacted blocks.
